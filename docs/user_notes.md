# ユーザーメモ・ログ

このファイルはユーザーから共有された事象・指摘を整理するための専用ノートです。AI 提案と分離して記録します。

## 1. Pylance 検知エラー（解消済み）
- PromptCard: `on_hover` に `HoverEvent` シグネチャ不一致の警告（ハンドラ型を合わせて解消）。
- Snackbar: `Page.snack_bar` 未定義扱い（`show_snack_bar` を使用、または `attr-defined` ignore で解消）。
- CardGridView: `Page.window_width` 未定義扱い（`page.window.width` 参照に変更）。
- CategorySelector: `dropdown.Option` に `value` 引数なし警告（`key` に統一）。
- EditorToolbar: `flet.icons` 未定義扱い（アイコン文字列指定または `ft.Icon(name=...)` に統一）。
- アプリ起動時エラー: "アプリケーションの初期化に失敗しました: module 'flet' has no attribute 'icons'"（`flet.icons` を参照したことが原因。アイコンは文字列指定または `ft.Icon(name=...)` で解消）。

## 2. 追加メモ欄
- 困りごと: 「次は〜をしましょうか」と AI から提案があり、着手するか判断に迷った。提案を採用しなかった結果、構築が不十分になった可能性があると感じている。
- 改善案:
	- 毎提案に対して「採用/保留/却下」を即決し、理由を 1 行で記録する（判断ログ化）。
	- 採用提案は小さなタスクに分解し、Issue/チェックリスト化して順次消化する。
	- 保留提案は期限を決め、期限までに再評価するリマインドを設定する。
	- 提案が複数ある場合は優先度（影響度×緊急度）で並べ、上位のみ着手する。
## 3. 困りごと＆改善案: ログ・エラー報告の手間

### 3-1. ターミナルログのコピペが面倒
- **困りごと**: ターミナル出力を選択・コピーしてチャットに貼り付ける作業が煩雑。スクロール必要な長いログは特に手間。
- **対策**:
  - **ログファイル直接参照**: ターミナル出力をファイルにリダイレクト（`python main.py | tee log.txt`）し、AI に「log.txt の内容を読んで」と指示。
  - **スクリーンショット**: 短い重要な出力はスクリーンショットで共有（VS Code の画面キャプチャ機能 Ctrl+Shift+P > Screenshot）。
  - **PowerShell 履歴**: `Get-Content (Get-PSReadlineOption).HistorySavePath` で最近のコマンドと出力を確認。
  - **Copilot に出力を読ませる**: 「今のターミナルの出力を分析して」と指示するだけ。AI はウィンドウ情報を持つ場合がある。

### 3-2. VS Code エラー（問題）の貼り付けが面倒
- **困りごと**: 「問題」パネルのエラー情報を JSON 形式で貼り付けることが煩雑。1 件ずつコピーしづらい。
- **対策**:
  - **「問題」パネルをパネル化**: VS Code の「問題」タブを独立させ、スクリーンショットで共有。
  - **JSON エクスポート**: 「問題」パネルの情報を VS Code API や拡張機能で JSON 出力し、ファイル保存。その後 AI に「errors.json の内容を分析して」と指示。
  - **Pylance 設定**: `.vscode/settings.json` に `"python.analysis.diagnosticSeverityOverrides"` を設定し、誤検知を抑制してから共有。
  - **スクリーンショット**: 全体を見たい場合はスクリーンショット、詳細分析が必要な場合は選択コピー＆ペーストで 3-5 件まとめて貼付。
  - **Copilot に指示**: 「VS Code の問題パネルの内容を全て分析して」と指示。Copilot は必要に応じて内容を出力させたり、参照ファイルから推論可能。

## 4. 困りごと&改善案: AI が実装した UI が動かない

### 4-1. 問題の本質
- **原因**: AI はアプリケーション実行環境に直接アクセスできない。実装したコードが実際に動作するか確認できないまま、仮定に基づいて出力している。
  - スクリーンショット・エラーメッセージなしで、AI は「これで動くはず」と盲目的に進む。
  - Flet や UI フレームワークの細かい API 仕様を誤解したまま実装される。
  - 実装と実際の要件のズレが積み重なり、UI 完成時に全く動かないという状況になる。

### 4-2. 対策

#### 短期（1-2 回の実装サイクル）
1. **早期テスト**: 実装の 1 ステップごとに実行してみる。エラーが出たら**すぐスクリーンショット・ログを共有**。
   - 例: `PromptCard` 実装後 → `CardGridView` と組み合わせる前に単体で動作確認。
2. **最小動作確認**: 「カードが表示される」「ボタンがクリックできる」など、1 機能ずつ検証してから次へ進む。
3. **Flet API の確認**: 使用する属性・メソッドについて、Flet 公式ドキュメント or AI に「このコードは Flet 0.28.3 で動くか確認して」と確認させる。

#### 中期（全体設計の見直し）
1. **テスト駆動開発**: UI 実装前に「カードが表示される」などのテストケースを pytest で書き、AI にそれを満たすコードを実装させる。
2. **UI コンポーネントの単体検証**: 各コンポーネント（`PromptCard`, `CardGridView`, `EditorToolbar`）を独立したダミーアプリで動作確認してから統合。
3. **仕様の数値化**: 「正方形カード」→ `width=300, height=300` のように、数値で確定させ、曖昧性を減らす。
4. **段階的統合**: UI を「ビュー → コンポーネント → イベント」の 3 層で実装し、各層でテストしてから結合。

#### 長期（AI との協調方法の改善）
1. **AI に「見させる」環境を作る**:
   - アプリ実行後、スクリーンショットを毎回共有（VS Code Simple Browser など）。
   - ログファイルを自動出力し、「log.txt を見て判断してください」と指示。
2. **責任を分ける**:
   - **AI の役**: ビジネスロジック（CRUD, 検索, バックアップ）→ テストで検証可能。
   - **ユーザー確認**: UI/UX（ボタン配置、色、アニメーション）→ ビジュアル確認必須。
3. **フィードバックループの自動化**:
   - 実装 → 実行 → エラーキャプチャ → 報告 のサイクルを短縮。
   - CI/CD パイプライン（GitHub Actions など）で自動テスト・ログ出力を仕組み化。

## 5. 困りごと&改善案: 繰り返し作業（プロンプト貼付 → コミット）の疲労

### 5-1. 問題の背景
- **現象**: 「プロンプトを AI に貼付 → 修正実装 → テスト → エラー発見 → プロンプト再調整 → 貼付」を何十回も繰り返す羽目になった。
- **原因**:
  - 初期設計が不十分で、実装中に要件が変わる（試行錯誤が多い）。
  - 1 回のコミットで複数機能を詰め込み、後戻りしづらくなる。
  - AI への指示が毎回バラバラで、期待値がズレやすい。

### 5-2. 対策

#### 短期（今後の開発を効率化）
1. **AI 指示テンプレートの定型化**:
   - 「Phase X 実装」のテンプレートを [docs/implementation_plan.md](docs/implementation_plan.md) に完全固定。
   - ユーザーは毎回同じテンプレートをコピペするだけ（カスタマイズ最小化）。
   - AI はテンプレートを見て「対象・要件・依存」を即座に理解。

2. **小粒度コミット**:
   - 1 機能 = 1 コミット（「カード表示」「編集フォーム」「コピー機能」を別々に）。
   - 各コミット後に動作確認 → 問題あれば即座に修正 → 再コミット。
   - 失敗が小さく、巻き戻しが楽になる。

3. **チェックリスト化**:
   - 各 Phase に「実装項目」「テスト項目」「確認事項」を箇条書き。
   - コンプリート状況を記録し、「あと何をするか」が一目瞭然に。
   - AI に「チェックリストの項目 1-3 を実装してください」と指示するだけ。

4. **段階的リリース**:
   - 完璧さより「動く」を優先（MVP: Minimum Viable Product）。
   - Phase 4-7 で「最小限の UI」を動かす → Phase 8-12 で磨く。
   - UI がカタチになることで、修正方向が明確になり、試行錯誤が減る。

#### 中期（開発フロー全体の改善）
1. **スクリプト化**:
   - `commit-phase.sh` など、よく使う Git コマンドをスクリプト化。
   - `bash commit-phase.sh 4 "CardGrid implementation"` で自動 commit & push。
   - タイプミスを減らし、手作業を削減。

2. **AI 指示の標準化**:
   - docs/ に「AI 指示テンプレート集」を作成。
   - 各テンプレートの成功パターンを記録し、次回以降の参考に。
   - 例: 「このテンプレートを使ったら 1 回で成功した」という履歴。

3. **定期的な振り返り**:
   - 週 1 回、Phase 完了時点で「試行錯誤の回数」「コミット数」を記録。
   - 回数が多い Phase は「設計が不十分だった」と判断し、次フェーズで改善。

#### 長期（AI とのワークフロー設計）
1. **対話型 AI エージェント**:
   - 単発の指示ではなく、「このフェーズを完成させて」と任せ、AI が段階的に実装 → テスト → 報告。
   - VS Code 拡張機能やカスタム Agent を使い、ユーザーの確認・承認フローを自動化。

2. **自動テスト → 自動コミット**:
   - テストが緑になったら自動で Git コミット。
   - ユーザーはコミット作業をスキップ。
   - 失敗時のみユーザー介入。

3. **責任分離**:
   - **AI**: ビジネスロジック＋単体テスト実装。
   - **ユーザー**: 動作確認＋UI 確認＋最終承認。
   - **自動**: テスト実行 → コミット → デプロイ。
